# ADR-0004：盘中行情与研究数据截止时间

状态：提议，待独立工程审查；本文记录 2026-11-13 用户确认的目标，不表示功能已实现。本文配套修订 SPEC、DATA_SERVICE、HARNESS、受影响技能、评测样例及目标数据/API 契约；目标规格通过审查与合并后仍须由后续任务实现与验收。本文取代 ADR-0003 中排除盘中实时行情的范围，不改变不得输出投资建议等边界。

## 背景

用户要求研究时同时获取盘中实时行情与各数据集当时最新可用的数据，并确认允许数据存储、展示及第三方模型处理。数据集发布频率不同：实时行情、收盘日线、财报、持仓和公告不能共用一个“实时”标签。厂商账号某次调用成功不能证明所有产品、字段、时延及历史版本能力。

现有计划创建时固定 `as_of`，但厂商请求在确认计划之后发生：新采集的行情 `available_at` 会晚于计划时点，按当前点时约束必须排除。直接放宽约束会引入未来数据；把请求时间显示成数据时间也不正确。

## 决定

1. 计划确认明确授权“开始采集后冻结一次最新可用数据”；计划的预览时点不能承诺最终行情值。采集完成后、分析开始前以数据库持久化的截止时间冻结快照；该时间必须不早于所有纳入记录的事件、接收、归档与可用时间。不能证明来源时间或可用时间的必需数据不得进入快照。
2. 截止时间一经落库，重试、恢复和报告各版本引用同一截止时间与快照，不因 worker 重启重新取数或更新截止时间。需要更近数据时创建新任务；取消与并发写入仍遵守 epoch、版本及步骤台账。
3. 行情须同时记录厂商、证券、价格及明确货币/单位、行情事件时间、接收时间、归档引用和延迟性质。只有授权能力、时区、事件语义和新鲜度阈值均已配置并验证时才能称盘中实时；缺失、延迟、过期、停牌、断线、限流、无权限须明确标注或按章节规则受限/弃权，不能由历史收盘价冒充实时价。盘后行情必须标识交易日及收盘状态。
4. 非实时数据按自身发布周期、公告日及允许使用的历史版本选择最近可用值。缺乏可靠的 PIT 或公告版本关联时，不能声称历史时点正确或将后来修订的值冒充当时已披露数据；财务必需字段不满足时按技能规则弃权。
5. 每个报告显示快照截止时间和各数据集实际来源、事件/披露或期间、系统接收/可用时间、延迟与限制。汇总值的展示不得暗示所有来源在同一时点更新；每个数字仍须绑定证据或计算记录。
6. 生产路径禁止 fixture、伪造补值和隐式回退至模拟数据。测试环境可显式运行标记为模拟的 fixture；真实数据失败应返回可诊断的缺失/错误状态。厂商账户级限流跨进程生效，不能通过多 worker 绕过。

## 契约迁移与实现顺序

- 计划和任务须区分计划预览时间与冻结截止时间：现有 `ResearchPlan.as_of` 和 `Task.as_of` 为必填非空时间，不能悄悄改变原含义。[0.4 草案](../../contracts/drafts/openapi-0.4.json)单独定义目标字段、未冻结时的可空状态及兼容语义，现行 0.3 契约保持不变；截止时间与快照必须原子绑定，旧任务保留原时点。未完成迁移前不启用该能力。
- 登记独立盘中行情数据集及证据字段；日线、估值和财报保留各自口径与更新频率，不把盘中快照伪装成完整日线。契约、技能版本、测试样例及实现一起升级。
- 研究启动应基于已登记授权能力执行确定性取数、归档、映射、质量检查和冻结；模型不决定取数。尚无真实适配器或声明不完整时，明确不可用。

### 跨存储发布和冻结协议

下面是实现目标；使用 PostgreSQL 的事务可见性作为冻结时刻的权威证据，而非假定 S3 和数据库能原子提交。

1. 获取并验证厂商响应，按内容哈希幂等写对象存储，确认回读或存储成功语义；对象内容为 SDK 可取得的原始响应或明确标注的解码响应。失败不得发布记录。再在数据库事务 A 中写不可变的对象引用、请求指纹、映射版本、记录版本与字段级血缘，唯一约束保证重试幂等。事务 A 提交前对象不得参与快照。
2. 事务 A 成功提交后，事务 B 才能登记发布标记并取得数据库时钟 `available_at`，因此这个时间不早于记录和血缘的提交。发布标记、版本与许可和质量状态绑定；事务 B 提交前该记录不可见。不能把采集时间、S3 写入完成时间或事务 A 内的事务开始时间冒充 `available_at`。对象写入成功但 A 失败可留待安全回收；A 成功而 B 失败或提交结果未知时，重试按唯一键查询并恢复，不能重复发布或用未发布记录。
3. 冻结事务在固定的 PostgreSQL MVCC 快照中读取已提交发布标记及相应记录，使用数据库时钟取得截止时间，并依据该视图筛选 `event_at`、`received_at`、`published_at`（适用时）及 `available_at` 不晚于截止的版本。所谓“最新可用”指冻结事务视图中已提交且满足许可、质量与时间规则的最新版本；并发中稍后才对该视图可见的提交留给下一任务。必须记录该视图形成的不可变记录版本清单，不能事后仅按时间戳重新查询重建该快照；发布标记的时间早于其事务最终提交并不意味着此前数据库视图已能看到它。
4. 冻结事务以任务当前 epoch 和 revision 为条件，原子写入截止时间、清单哈希及清单引用；并发或旧 epoch 只能有一个赢家，失败者读取赢家结果，不重新冻结。若清单需存对象存储，先写入内容寻址对象，再在事务中绑定哈希和引用；回滚或失败可能遗留无引用对象，不能暴露为已冻结快照。冻结后重试只读取并验哈希；缺对象或哈希不符应失败并告警，不能用新数据静默替换。
5. 许可撤销、映射修订和质量隔离不得改写既有版本或冻结清单；报告访问与模型发送须按当前许可重新授权，已撤销用途不可继续使用。对象回收必须检查记录和快照引用并遵守保留策略，不能删除仍被引用的数据。

数据库时钟及供应商事件时间须具备受控同步与偏差监测；存在未来时间或不可解释偏差时不通过时间校验。系统接收时间来自受控采集时钟，不能把 SDK 返回日期轴直接当成可用时间。原有记录若没有可证明的对象、血缘和提交时点，不能回填成已验证实时数据。

### 版本兼容与迁移目标

- 保留现有 API 0.3 响应及计划 `as_of` 含义；通过 `Accept: application/vnd.vera.v0.4+json` 显式协商目标 0.4 业务 JSON，缺省 `application/json` 保持 0.3；成功响应的 `Content-Type` 必须匹配并设置 `Vary: Accept`。客户端须检查响应类型，因为已有服务器可能忽略 `Accept`。0.3 的严格客户端不能收到新增的响应字段，也不能选择 1.1 实时技能；客户端未升级时不能静默将计划从固定时点改成采集后冻结。新建 0.4 计划使用 `collect_latest`，读取历史任务可返回 `fixed_legacy`。请求、创建计划与确认任务的版本必须一致；实现 PR 必须生成匹配客户端并测试旧版、未支持版本、混用版本和中间缓存。无协商实现前不得启用新行为。
- 新版计划明确 `snapshot_mode=collect_latest`，将模式、预览时点和技能版本纳入计划哈希；确认必须与该哈希一致。新任务冻结前 `snapshot_as_of=null`，冻结事务提交后才返回非空值。旧计划和任务回填 `fixed_legacy`，保留旧的计划哈希、原 `as_of`、既有清单与报告，不因升级重采或改写。模式/截止时间/清单须有数据库条件约束，历史非法或缺少可验证快照的记录必须显式标记、隔离或保留原不可用状态，不能伪造。
- 采用向后兼容的 expand → 双版本读写与回填 → 验证 → 切换 → 清理顺序，切换前验证历史任务、执行中的任务与重复确认；新写入只在迁移及应用读写能力均部署后启用。回滚只能关闭新计划创建并保留已写入新列和快照；旧二进制不得处理已创建的 `collect_latest` 任务，避免把预览时点当成冻结截止。清理旧字段前须确认无旧 worker 和旧客户端依赖。

### 章节结果矩阵

当计划明确要求盘中实时，证券、行业或市场对应的行情为必需：交易中只有已授权、事件时点可信、延迟性质确认为实时且满足注册阈值的快照才满足该要求。缺失、过期、未知时点、延迟或无权限时，该必需部分 unavailable，依技能规则弃权；不能把历史收盘或 fixture 展示为实时。收盘、休市与停牌时不承诺发生新的实时成交：可展示经过验证的最近行情及交易状态、交易日和事件时间，但应明确非当前交易中的新成交；若计划明确要求的是交易中实时成交而非最近可用行情，则仍不满足。交易状态本身未知时不得推断休市或停牌。

未要求实时的计划按原技能的必需/可选规则判断，已验证且获许可的延迟行情可作为延迟行情展示，未知延迟必须明确未知；非实时的财报和资金数据按实际可用版本与各自周期展示。必需数据集缺失使相应章节 unavailable 并按技能弃权；仅可选部分缺失时交付 limited 并列明原因。上述判断不能把需要披露时间及修订关联的财报当成已验证版本。

## 验收样例

模拟交易日盘中任务：计划与确认间隔超过行情新鲜度时，采集阶段重新取数，截止时间不早于事件与接收时间；过期、缺失、未授权与服务故障时不能展示旧值为实时。重试和重启沿用已冻结快照。财报报告期早于截止而公告晚于截止、或只能取得修订后值时，不能进入当时快照。盘后行情须标记收盘时点；无行情权限时明确受限或弃权。
